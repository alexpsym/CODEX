DEFECT 1: BYBIT SAME-SNAPSHOT LIQUIDITY

Root cause:

- render/atr_scanner.py previously treated ticker bid/ask/spread as final gates, stored the ticker midpoint, and later measured a separately fetched order book around that older midpoint. A fast price move could therefore produce zero in-band depth and false exclusion, while spread and depth described different snapshots.

Exact fix:

- Ticker processing now uses only turnover24h as the comparable 24-hour quote-turnover source and prefilter. volume24h remains unused. Ticker bid, ask, spread, and midpoint neither exclude a turnover-qualified symbol nor influence its depth.
- Every turnover-qualified, non-manually-excluded instrument reaches the existing paced/concurrent order-book stage.
- calculate_orderbook_depth now parses one fresh order-book response and derives authoritative best_bid, best_ask, midpoint, spread_pct, bid_depth_usdt, ask_depth_usdt, book timestamp, and age from that response alone.
- Midpoint is `(best bid + best ask) / 2`; spread is `(best ask - best bid) / midpoint * 100`; bid/ask depth remains price-times-quantity quote notional inside the inclusive configured band around that midpoint.
- Final gates run deterministically against that same snapshot: spread above maximum, bid depth below minimum, then ask depth below minimum. Existing comparison semantics remain spread <= maximum and each depth >= minimum.
- Authoritative best bid/ask, midpoint, spread, depth, timestamp, and age remain in qualified rows and valid liquidity/ATR-excluded payload rows. The unchanged UI reads the corrected spread/depth fields; no JavaScript change was needed.
- Missing timestamp, stale, crossed, empty, malformed, non-finite, zero, or negative order books fail closed as missing_invalid_market_data with a scoped order-book error. No stale ticker liquidity value is substituted.
- Existing request pacing, concurrency, shared refresh, caching, settings, manual exclusions, six ATR timeframes, last-known-good behavior, Top 10 ranking, and public-only source behavior are unchanged.

DEFECT 2: PEPPERSTONE FALSE GLOBAL STALE

Root cause:

- mt5-clone/atr_percent_window.py compared last_successful_refresh_epoch_ms with the desktop clock and forced global Stale after 30 seconds. That timestamp advances only when a new fully closed bar produces a new ATR value, so healthy cached Ready values falsely became Stale between minute closes or while markets were closed.

Exact fix:

- Added pure classify_window_state logic that uses the local feed file mtime as the EA-to-window heartbeat, with the existing tolerance `max(5 seconds, refresh_ms * 6 // 1000)`.
- State priority is: old feed file or explicit forex row/timeframe Stale -> Stale; otherwise Error -> Error; otherwise Loading or no successful parsed ATR value -> Loading; otherwise Ready.
- Both aggregate row status and all six per-timeframe states are inspected.
- last_successful_refresh, last_successful_refresh_epoch_ms, and generated_at remain informational broker/closed-bar metadata only. They are not clock-based freshness authorities.
- The existing MQL5 EA already calls ExportATRFeed on every healthy timer pass and closes the written feed, so file mtime is an adequate local heartbeat. MarketWatchATRPercentFeed.mq5 did not need modification; its closed-bar caching and all six calculations remain unchanged.
- The Tk UI, columns, ranking, Top 10, refresh cadence, last-known-good behavior, feed identity, and separation from Market Spread are unchanged.
