1. Render-owned executor lifecycle
- Replaced the fixed 30-second authoritative-restoration timeout with event-driven coordination. FX Weekend now waits for the actual restoration signal and the existing durability gate, then starts automatically even when restoration takes longer than 30 seconds.
- Render remains the sole FX Weekend execution owner. Local profiles and browser tabs do not start or own an executor.
- Added a unique executor instance token for every child spawn and validate both the managed PID and the per-spawn token before accepting a heartbeat.
- Added a bounded first-heartbeat startup grace. A newly spawned current child is amber while starting; a stale heartbeat from an old PID or old instance is never accepted as current.
- Serialized the complete ManagedScript start/stop lifecycle. A concurrent restart cannot replace a child while old-child termination is still awaiting cleanup, and old cleanup cannot terminate or clear the replacement child's PID, token, process, or port.
- Restore/autostart and supervisor races dispatch exactly one start.

2. Heartbeat and supervisor reliability
- The scheduler now writes a heartbeat at least every 30 seconds throughout intentional sleep and failure backoff, including a configured 300-second delay.
- Runtime status records the executor PID, instance token, stable executor_started_at, sleeping flag, sleep reason, sleep start/end, and remaining scheduled delay.
- The backend stale threshold is derived from the configured check interval and maximum retry backoff plus a safety margin. With the checked-in 60-second interval and 300-second maximum backoff, the threshold is 420 seconds.
- A healthy sleeping executor keeps the same PID, instance token, and executor_started_at and is not stopped or restarted by the supervisor.
- Render logs now explicitly record:
  - FX_WEEKEND_START_REQUESTED with reason;
  - FX_WEEKEND_CHILD_SPAWNED with PID and working directory;
  - FX_WEEKEND_HEARTBEAT_CONFIRMED with PID and heartbeat diagnostics;
  - FX_WEEKEND_OPERATIONAL_STARTUP with PID, executor start time, health, and runtime state;
  - termination/restart requests and completions with the exact reason.

3. Backend-authoritative dashboard health
- The FX Weekend dashboard indicator is driven only by backend process, heartbeat, credential, account, and execution status.
- Browser-tab lookup occurs only for other dashboard tools. Opening, closing, focusing, or refreshing an FX Weekend tab cannot change its status.
- Health mapping is now:
  - green: enabled managed process running with the current instance's fresh heartbeat;
  - amber: current process starting, or a healthy process reporting a prior missed cutoff/closed market;
  - red: stopped process, genuinely stale/wrong-instance heartbeat, unavailable credentials, API failure, partial closure failure, or retry pending;
  - disabled: explicitly labelled "Disabled" with a neutral disabled indicator rather than presented as a crash.
- Healthy missed-cutoff/closed-market state remains operational but visibly amber.

4. Manual liquidation UX and safety
- Renamed "Run now" to "Run liquidation now".
- The FX Weekend page explicitly states that this action immediately requests liquidation and is not a scheduler start/enable button.
- The page prevents normal form navigation, sends the request with fetch, and displays success, account states, or errors in an aria-live result panel instead of navigating to raw JSON.
- The FX Weekend liquidation proxy has a dedicated configurable read timeout, defaulting to 600 seconds. Other proxy routes retain their 30-second timeout.
- Scheduled and manual liquidation are serialized. An overlapping manual request returns HTTP 409 without duplicate OANDA close work or scheduler-state mutation.
- Manual Live liquidation outside the configured closure window remains blocked with HTTP 409 and does not alter heartbeat, retry counters, scheduler status, or the continuously running executor.
- Every Live close request checks the market-close deadline immediately before the PUT. No close request is sent after the window boundary, including when the boundary arrives mid-batch.

5. Demo and Live closure guarantees
- Selected accounts run in deterministic Demo-then-Live order, and a failure in one account does not suppress reporting or processing of the other.
- Both position and trade closure modes fetch the selected account's open scope, submit mocked close requests during tests, and authoritatively re-fetch both positions and trades after the attempt.
- Overall success requires every selected account to be re-fetched and verified flat. Close-response success alone is never treated as proof.
- Recoverable closure failures retain retry headroom before market close. During the closure phase, failure backoff is capped to 25 percent of the remaining window rather than sleeping until the boundary.
- The configured Brisbane cutoffs remain unchanged: 05:00 during US DST and 06:00 during US standard time.
