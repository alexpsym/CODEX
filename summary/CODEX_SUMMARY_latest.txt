1. TradingView Forex markers
- pinescripts/custom_indicator.pine now defaults the adjustable recent-range candle clearance to 0.06 and uses a 40-tick minimum for session and historical marker gaps.
- Session marker times, DST handling, Brisbane-weekend filtering, labels, 80-bar range, 0.60 half-length multiplier, dotted black width-2 styling, and the <=30-minute session visibility gate remain unchanged.
- One split upper/lower historical marker is mapped for every requested pair/date. Pair selection uses syminfo.basecurrency plus syminfo.currency, so it is independent of OANDA, FXCM, FOREXCOM, or other ticker prefixes.
- Every historical timestamp uses exact GMT midnight and xloc.bar_time. Exact switch matches prevent reversed or unlisted pairs from receiving a marker.
- Historical markers have no label or setting, are independent of showSessionLines and timeframe gates, and use a persistent draw-once guard to prevent duplicate objects.
- TradingView compilation was not available locally. Static source tests passed, but they do not prove Pine compilation.
- A feed limitation remains unavoidable: when the loaded broker history has no bar spanning the requested timestamp, the marker is not moved to the broker's first available candle and no substitute history is invented.

2. Master Journal datetime serialization and cache durability
- read_master_journal_source() and read_master_journal_manual_overrides() now pass Move to Break Even Time and Move to Profit Time through the existing _excel_datetime_to_iso() helper.
- Excel datetime/date values become ISO strings, existing strings remain strings, and blanks remain blank strings. No json.dumps(default=str) or broad fallback was introduced.
- _set_trading_journal_rows() now assigns _TRADING_JOURNAL_CACHE only after the durable JSON write succeeds, so a failed write leaves both memory and disk at the previous state.
- The checked-in journal regression read returned exactly 1,544 rows, contained no datetime/date objects anywhere in the source payload, passed json.dumps(), and preserved the workbook hash.

3. OANDA complete-history backfill
- Master-journal single-file mode no longer calls _append_oanda_export_rows_to_local_workbook() and does not create OANDA DEMO.xlsx or OANDA LIVE.xlsx.
- Completed exports are passed to _import_uploaded_trading_journal_file() with the resolved demo/live mode explicitly. This reuses the existing authoritative lock check, parsing, P/L inference, canonical OANDA replacement, upsert, pending-row bridge, workbook sync, rollback, row-ID verification, and GitHub journal-sync transaction.
- OANDA CSV parsing now honors the explicit account mode even when the filename has no demo/live hint.
- The endpoint performs an additional Trading Journal.xlsx check for every parsed OANDA trade row ID and verifies the authoritative snapshot contains the correct OANDA account balance matching the export's latest balance.
- Repeated identical backfills report zero new/updated rows and preserve existing trade/cashflow row IDs without creating a broker workbook.
- Parse, workbook-lock/import, sync, row-verification, and snapshot/balance failures return JSON-safe structured responses with the existing history-page response fields.
- The legacy separate-workbook branch remains available only outside master-journal single-file mode.

4. Export/backfill browser status
- render/static/history_page.js resolves the completed export download URL before starting OANDA backfill.
- A backfill failure now says the export completed but Trading Journal backfill failed; it leaves a manual CSV download link available.
- Successful behavior remains ordered as requested: export completion, authoritative journal backfill/verification, then automatic CSV download.
- Automatic download failures continue to expose a manual download link.
