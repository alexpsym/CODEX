1. Root cause and authoritative import transaction
- The parsed OANDA transaction-export account balance is now carried beside pending manual-import rows through the rollback-protected authoritative master-journal transaction.
- Both normal imports and duplicate/no-op imports build the workbook snapshot with the parsed balance seed before updating journal/Trading Journal.xlsx.
- The importer verifies the parsed balance before workbook sync, rereads Account Balances from the saved workbook, then forces a master-workbook snapshot rebuild and verifies the value and provenance again before completing SQLite persistence and GitHub sync.
- A failed value or provenance check remains inside the existing rollback scope. Row state, workbook bytes, view cache/SQLite state, and pending import bridges are restored locally. Rollback reporting does not claim GitHub state was restored when a remote sync had started and failed.
- Imports without a parsed account balance retain their prior workflow and focused compatibility coverage.

2. Durable workbook balance provenance
- Account Balances now stores hidden workbook metadata keyed by canonical account. It preserves both balance_source and a wall-clock comparison timestamp without changing the visible workbook layout or adding a sheet.
- read_master_journal_source() recovers this metadata in streaming/read-only mode, so an OANDA transaction-export balance remains authoritative after workbook reread and application restart instead of degrading to stats2_account_balances.
- The separate comparison timestamp matches the established Trade Log wall-clock serialization while leaving the visible As Of value unchanged.
- OANDA transaction-export balances are ranked as authoritative account-summary inputs during balance deduplication.
- A later authoritative account seed now overrides the final trade timeline even when the account has no cashflow ledger entry. An equally timed OANDA export seed also preserves its stronger provenance.
- The final trade row's balance_after_trade remains the actual closed-trade balance; it is not overwritten with a later financing/deposit/withdrawal/transfer balance.

3. Truthful endpoint semantics
- oanda_export_rows_persisted, oanda_export_balance_applied, and snapshot_visible are explicit state fields and are no longer derived from the overall ok flag.
- If endpoint-level verification fails after the authoritative importer committed and verified rows, the response retains rows_persisted:true.
- Balance application requires the rebuilt snapshot to match both the export value and oanda_transaction_export_balance provenance.
- Snapshot verification exceptions preserve already verified authoritative importer state instead of converting known persisted/applied state into false values.
- The legacy separate-workbook branch remains available outside master-journal mode and now reports row, balance, and visibility state explicitly.

4. Single-file and browser behavior
- Master-journal mode continues to update only journal/Trading Journal.xlsx. It does not create journal/OANDA LIVE.xlsx or journal/OANDA DEMO.xlsx.
- The legacy separate-workbook implementation remains outside master-journal mode.
- render/static/history_page.js was not changed. Successful backfill still precedes automatic CSV download; failed backfill still says the export completed and retains the manual download link.
- The completed Pine, Move-to-Time datetime serialization, failed-write cache durability, equity cache, and browser-download implementations were not changed.
