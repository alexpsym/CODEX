2. Incremental import implementation
- Added a strict current-schema/current-master-workbook incremental path for small Oanda transaction exports. It uses the already-read preflight workbook source, computes normalized state deltas, and caps a transaction at 25 affected/state-delta rows.
- Immediate duplicate imports compare uploaded row projections and the account balance against that preflight source. They skip JSON upsert, full snapshot/statistics work, workbook replacement, SQLite persistence, full verification, and GitHub synchronization.
- Changed imports update only the affected canonical Trade Log rows and the imported Oanda account balance. Unchanged parsed history rows are not retimestamped, rewritten, or sent through row-context side effects.
- Genuine metadata-only JSON changes remain durable but do not cause unrelated workbook or SQLite trade-row updates. The existing repaired Oanda row contributes one genuine metadata enrichment in the live-derived benchmark; only the newly imported row(s) are workbook-affected.
- Incremental SQLite persistence updates only workbook-affected trade rows plus the balance. Full snapshot/derived work is queued explicitly after the primary stores are durable; GitHub workbook synchronization is explicitly deferred to that derived refresh.
- Safe incremental ineligibility can use the existing full fallback. Unsafe workbook-owned content (for example a managed formula that cannot be preserved/recalculated) refuses the import and rolls back instead of risking manual content.

3. Durable commit, recovery, locking, and status
- Durable incremental intent is written before JSON mutation and stores a bounded replay payload (maximum 25 rows / 256 KiB) with prepared, json_committed, workbook_committed, and incremental_committed phases.
- Restart recovery replays the staged JSON rows, atomic workbook update, balance, and SQLite update before any full derived refresh. Replay failures remain retryable and can never be reported as a stale full-refresh success.
- A different import cannot replace a nonterminal recovered transaction. Public status/import responses expose only transaction metadata, phases, row counts/IDs, and timestamps; staged row and balance payloads remain internal.
- The import owns a reentrant workbook-writer lock from authoritative read/backup through commit or rollback. A stale backup cannot overwrite another successful workbook writer.
- Once SQLite has committed, a later state/defer write failure no longer rewinds JSON/workbook. The coherent primary commit and workbook_committed intent remain available for idempotent replay.
- Exhausted recovery retries are actionable: the next import requeues the same retained transaction in place, returns an explicit recovery-in-progress 409, and a later retry proceeds after replay. Invalid retained payloads remain explicitly and safely blocked.
- Derived refresh generations coalesce affected IDs, use bounded exponential retry, expose queued/running/retrying/failed/succeeded state, recover across restart, and clear the staged payload only after successful derived completion.

4. Atomic workbook and authored-content preservation
- The incremental workbook helper writes a candidate, reloads and verifies it, fsyncs it, and atomically replaces the source only after row, balance, formula, name, structure, chart, and range checks pass.
- Existing rows are updated in place by stable Row ID. Appends reserve every blank target before mutation, preserve authored blank-row presentation, allow identical canonical preformatting, and refuse content/comments/links/merges or differing custom presentation that would be overwritten.
- Authored conditional-format rules sharing the generated A4:AX... range survive. Only the two exact tool-owned win/loss rules are replaced, their priorities are retained, and the generated rules remain unique.
- All xl/charts/* parts are restored byte-for-byte, and the chart part/relationship sets are verified. The real-workbook audit confirmed chart parts, drawing parts, and every relationship part remain byte-identical.
- Authored Trade Log formula caches are keyed by stable Row ID and logical header. A cached value is transplanted only when formula OOXML is unchanged and a bounded deterministic same-sheet dependency signature is unchanged; data_only reads and statistics therefore retain safe manual formula results.
- Formulas with affected dependencies, cross-sheet/named/structured/volatile/unprovable references, or cycles are refused on the incremental path. Array/shared/data-table/dynamic formula representations and any managed STATS2 Account/Currency/Balance/As Of formula are refused before save unless exact safe preservation is available. The original workbook remains byte-identical on refusal.
- Preservation-mode derived rebuilds restore authored normal Trade Log formulas by stable Row ID without restoring stale ordinary numeric values. Safe unchanged caches move with the Row ID; stale caches are not copied; calcMode/fullCalcOnLoad remain intact.
- Balance-only updates preserve the complete Trade Log presentation signature. Manual borders, fills, number formats, protection, comments, hyperlinks, row heights, column widths, freeze panes, defined names, chart formulas/anchors, sheet views, and layout remain protected.
